# 审计入图状态与变更统计设计

## 范围与现状

修改 `flowscope-storage` 的正式血缘结果、`flowscope-cli` 的受理/审计 API，以及 `app` 审计状态展示。解析器算法、个人使用图的权限和存储语义保持现有契约。

当前代码的入图链路是 `/api/analyze` → SQLite 存储事件 → Rust 后台任务 → Neo4j Bolt 事务，并非调用独立的 HTTP 入图接口。本任务把“请求入图”定义为通过解析和入图前置检查、进入正式血缘写入流程，不把请求解析接口本身称为已请求入图。

## 状态判定

内部事件状态继续表达投递、重试和历史原始结果。对审计列表、详情、事件的正式入图结果以及筛选，使用统一的业务分类；个人 `usageStatus` 独立处理。`lineage_reason` / `lineageReason` 单独解释正式图决定，保留 `policy_reason` / `reason` 的原始个人使用诊断。

| 条件 | 对外业务结果 | 页面 |
| --- | --- | --- |
| 无可靠历史事件/状态证据 | `unknown`，保留内部证据缺失语义 | 空白，无徽标，说明中不列未知项 |
| 普通发布 SQL 解析失败 | `not_requested` | 未请求入图，展示解析原因 |
| 策略动作不是正式发布，或写入前复核禁止发布 | `not_requested` | 未请求入图，解释策略原因 |
| 解析成功，但正式入图前置质量/元数据检查不满足 | `not_requested` | 未请求入图，解释检查原因 |
| 有效发布请求已排队、执行中或等待可重试异常恢复 | `queued` | 待入图 |
| 正式血缘事务已经提交或已回查到对应提交回执 | `committed` | 已入图 |
| 进入正式入图流程后被旧版本等存储规则拒绝，或遇到终止错误 | `failed` | 未入图，展示实际拒绝/错误原因 |

“未入图”表示已经尝试后没有成功完成；可重试异常尚未终止时继续显示待入图。解析失败和策略禁止不能归为正式存储失败。已确认的事务提交证据不能被后续策略变化覆盖。

新请求在正式入队前执行纯前置检查，复用存储层现有质量判断，存储层保留事务内的防御校验。解析或质量不满足的候选可以保存 SQLite 审计和终态事件，但不得进入 `next()` 的可执行队列、不得调用正式 Neo4j 更新。保留事件身份和内容校验，避免破坏已有幂等语义。正式撤回事件不是普通 SQL 发布，不新增解析器前提，也不改变其现有撤回权限与事务行为。

历史 `blocked` / `blocked_policy` 根据保存的解析结果与原因映射，而非把所有旧 `blocked` 一概改名。缺少证据时保持 unknown，前端留空；不猜测历史曾发生的动作。旧原因不足以判定时保留原事件细节，不能虚构准确失败阶段。

`lineage_status` 服务端筛选必须使用与展示相同的有效状态表达式，计数与分页行保持 SQLite 同一读快照。兼容旧筛选参数，但 UI 只呈现四个明确状态；旧 URL 的未知条件也必须有明确可清除的筛选表达，不能静默扩大为全量结果。

## 实际变更统计

### 口径

用户已确认按实际新增、更新、删除分别计数。统计对象是业务血缘节点与投影关系；内部事件、版本、事实、锁和通用标记不计入业务统计。

- 节点按业务 label 类别：`M_TABLE`、`M_COL:Physical`、`M_COL:Derived`、`CTE`、`TEMPLATE`、`SYNC`、`LINEAGE_OUTPUT`。每个节点按稳定身份去重，多标签节点不能在总数中重复累加。
- 关系按 Neo4j 关系类型：现有投影支持 `READS_FROM`、`REF_TABLE_COL`、`REF_TEP`、`DERIVES_COL`、`JOINS_WITH`、`CONTROLS_COL`。
- 新增：本次提交前不存在，提交后存在。
- 更新：提交前后是同一业务对象，业务属性发生变化。单独刷新 `utime` 等维护属性不算业务更新。
- 删除：提交前存在，提交后消失。现有写入器不删除共享业务节点，本任务不增加节点清理规则。
- 本次无变化：分组及总数为 0，并说明当前血缘已经是该版本。

统计限定在本次事件的业务对象与受影响旧投影范围，不能扫描整个图计算差值，也不能用 `Snapshot.entities` / `Snapshot.facts` 的长度替代实际变更。单条写入语句返回修改前值、创建标记或明确计数；在事务内根据稳定身份去重。旧关系集合在已有共享边锁保护后获取；节点统计也必须在实际写锁/原子写入返回的证据下计算，避免并发请求同时声称创建同一节点。

### 结果与持久化

在 `ApplyOutcome` 新增可选 `graphChanges`，包含节点和关系的总数及分组，每组有 `created`、`updated`、`deleted`。可选字段支持读取旧事件结果，缺失代表未记录，不能自动补零。

统计和业务修改在同一个 Neo4j 事务中生成，并写入该事件的 `outcome_json`。只有事务提交成功，或 `receipt()` 回查确认提交，才允许对外展示为成功统计。失败与回滚不产生成功统计。

SQLite `lineage_events.outcome` 继续保存完整提交结果，审计列表/详情通过事件关联暴露 `graph_changes`。新增可空 `audit_log.lineage_decision` 保存新请求明确的只解析决定，区分匿名新请求与历史无证据记录；历史 NULL 不回填。不在每次打开提示时查询 Neo4j。字段命名依现有结果 camelCase、审计字段 snake_case 的约定。

同一 event 的幂等回读返回原结果和原统计，不能累加或改写成零；新 event 遇到同版本同内容 `already_current` 时，返回本次无变更统计。一个事件关联多条审计行时，提示明确写“本次入图请求”，不误称单个文件的变更量。

## 界面与交互

- 保留现有状态徽标和说明面板，只展示四种业务状态；合并原 failed 与真正执行失败类 blocked 的页面含义。
- `committed` 的悬浮/聚焦/点击面板展示“新增 / 更新 / 删除”三列，按节点 label 和关系类型分组。旧成功记录缺统计显示“该次入图未记录变更统计”。
- `not_requested` 也允许查看解析、质量或策略原因，修正当前组件主动排除该状态原因面板的行为。
- `failed` 展示完整原因；已知代码翻译为中文，原始原因可展开，不能推测未记录的网络错误阶段。
- 提示继续支持键盘、点击、触屏和滚动，阻止事件传播到审计行。轮询刷新不能关闭用户已固定的提示，也不能让表格闪烁。

本任务沿用现有组件和视觉约定，核心评审内容是状态含义、分组表与交互证据。

## 兼容、风险与回退

- 原始事件证据保留，业务状态映射集中维护；旧 JSON 缺少统计可读取，未知状态在页面留空。
- 列表、详情和 SQL 筛选必须通过相同用例证明分类一致；只修改前端标签不足以满足需求。
- 统计不能改变现有原子替换、共享节点保护、来源版本与撤回规则，不能在失败后另外提交统计。
- 新增持久化字段采用可选结果 JSON，回退应用版本不需要删除审计表或改写历史。
- 实施与验证使用任务独占的本地服务和隔离 Neo4j，不影响当前运行服务或生产图。
