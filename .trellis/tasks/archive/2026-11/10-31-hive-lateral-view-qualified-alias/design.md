# 技术方案

## 根因与边界

错误位于正式 Core 的名称绑定与引用解析阶段。现实现以输出列名为唯一键，未登记 LateralView 的表别名。全局重复拒绝将合法的 tmp.index_1 / tmp1.index_1 当成歧义。修复不涉及 SQL 文本预处理、HTTP 协议或新增边类型。

## 绑定与解析

1. 在每个 SELECT scope 中保留 LATERAL VIEW 表别名、输出列名与已解析输入来源的关联；标识符规范化复用现有规则。不能把虚拟输出加入物理来源表。
2. 分开处理表别名限定查找和无前缀输出查找。按 (表别名, 输出列名) 查找可区分重名输出；无前缀查找保留所有候选，只有唯一候选可解析。重复声明只更新候选状态，实际引用时才决定报错。
3. 保留原 explode(struct) 结构输出访问 r.goods，区别于表别名限定访问 e.r。遵循既有真实关系别名优先规则；不得将任意 e.unknown 映射到 UDTF 的输入。
4. 用明确的解析状态区分非 UDTF 引用、已解析、歧义和已知虚拟表下的未知输出。歧义或未知输出不能落回普通字段解析而制造来源。
5. 覆盖投影、WHERE 与后续 UDTF 输入；值来源与 window_control 采用一致绑定，作用域出栈后清理。常量输入没有物理根时，也不能跳过输出名登记。
6. posexplode 的位置列属于函数生成的位置，不能作为原表 index_1 字段或误当数组元素直传。复用现有 Derivation/表达式规则描述其输入依赖，不新增边类型。值列分别保留对应数组来源。

## 兼容与风险

不能只删除 duplicate 检查，也不能将 HashMap 后写覆盖前写。需要防止虚拟表别名遮蔽、嵌套 SELECT 绑定泄漏、无 Schema 时推断出伪物理字段。保持目前对物理关系名称的优先级；不扩展为通用 Hive 全量名称校验器。
