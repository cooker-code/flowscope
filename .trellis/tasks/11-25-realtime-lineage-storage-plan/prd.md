# 方案 B：FlowScope Rust 实时解析与独立存储层规划

## 目标与本轮范围

用户希望 FlowScope 解析后实时更新血缘，抽离可写 Neo4j、后续可扩展 PostgreSQL 的存储层。先利用现有 Neo4j 图验证。本轮先了解背景和现行机制，给出完整规划；2026-11-25 同意创建 Trellis task 并进入规划。

用户随后明确选择方案 B：在 FlowScope 内新增独立 Rust 存储层，直接连接 Neo4j；neo4j-http-service 仅作为图结构、入图规则与对照依据。新链路不依赖 Python 服务、Python 解释器或 Python 子进程。

2026-11-25 用户批准开始实现。本次已完成 Rust 存储层、统一 analyze 的 token 策略、策略页面及隔离验证；完整路线图中的来源订阅、CSV 回填、生产切换和 PG 留待后续。实现与自动验证证据见 [implementation-result.md](./implementation-result.md)。生产图及现有维护自动化未修改。

## 已核实事实

- Hive `default.sql_analyze` 的 Java 实现位于 `bigdata-hive-udf`。它逐次请求 FlowScope `/api/analyze` 并返回 JSON，没有 Neo4j 写入。
- 数仓 `dwd_conan_table_meta_da.hql` 从每日快照抽取 Change、Change-export、Mario 模板，调用 UDF，将 SQL、解析 JSON、任务及表元数据写入日期分区。
- `neo4j-http-service/src/batch` 从两份 CSV 组装 Neo4j 节点和边；`src/service` 目前提供检索，没有血缘写入 HTTP 接口。
- 当前 FlowScope 分析接口返回解析结果，并可异步写 SQLite 审计；审计写入不保证投递，结果超过 1 MiB 会截断。
- 生产只读回查：FlowScope 0.7.0、Hive 方言、无外部 schema、SQLite 审计启用；Neo4j 5.27.0 Community。
- 生产图有 4,324 个 M_TABLE、70,766 个 Physical、378 个 TEMPLATE、404 个 SYNC。M_TABLE 最大 utime 为 2026-10-27 19:30:44.658（UTC+8），此值不等于源分区日期。
- 本地代码已有 LINEAGE_SCOPE / OWNS_LINEAGE，但生产图没有该标签、关系或唯一约束；不能把本地实现视为生产已迁移。
- 现有维护自动化启用，工作日 10:00 处理昨日分区。最近读到的 2026-11-24 运行记录及日志表明 uv.lock 不匹配，入图前已停止；“设计为 T+1”不代表“当前持续每日更新”。

## 需求

- R1：解析与存储职责分离，数据库连接、模型转换和版本替换不进入 flowscope-core。
- R2：Neo4j 先行验证，保留 PostgreSQL 适配入口；首期无需实现双库同时写入。
- R3：覆盖表、字段、CTE、表达式、JOIN、过滤条件、窗口控制依赖及任务/模板/同步元数据的已有语义，不能只落节点和普通值血缘。
- R4：明确实时触发来源、稳定来源身份、版本顺序、失败语义、删除与历史可见性。
- R5：同一来源重复投递幂等、乱序不回退、共享节点不误删、失败不暴露半份新血缘。
- R6：利用现有图结构和查询接口做对照，隔离图通过后才计划生产迁移。
- R7：离线补偿与实时更新遵守同一版本规则，旧分区重跑不能覆盖更新的实时版本。
- R8（用户已确认）：临时解析保留独立记录，只有可信来源更新正式图。正式任务 A→T、临时解析 B→T 时，正式图仍为 A→T。
- R9（用户已确认）：存储实现属于 FlowScope Rust workspace，新增 flowscope-storage crate；通过 Rust 驱动直连 Neo4j。后续 PG 复用同一标准模型与存储契约；不调用 neo4j-http-service 完成写入。
- R10（用户新增要求）：提供服务端可配置策略页面，以 token 绑定的可信调用主体决定写入行为；区分调度更新正式血缘、个人记录查询使用关系，以及只解析/独立记录。sourceName、文件名或请求自报类型不能提权；解析结果、本地受理、正式图或使用记录的提交状态分别表达。
- R11（用户新增要求）：统一围绕现有 `/api/analyze` 规划身份和存储。调度 token 可按已启用策略自动更新正式图；个人 token 可增加“谁提交了哪些表的查询、如何使用”的图记录，不能修改正式生产血缘。
- R12（用户反馈后修订）：基于 SQLite 已有审计提供策略管理和判定回溯；管理员管理调用主体/token、启用状态和默认动作，预览并保存生效。移除调用方环境、允许/禁止来源及表范围限制。解析历史和策略定义分别保存，修改策略不自动发布历史 SQL。
- R13：个人图记录首先证明提交解析，不能称为已实际执行的查询。保留原 SQL、解析条件/角色和完成度；实际执行成功需来自受信执行回执。历史无身份的 SQLite 行不能凭 sourceName/IP 直接归属到个人。
- R14（用户页面反馈）：支持物理删除调用方及全部 token，删除后旧 token 不再受理；保留历史审计和已提交图数据。列表展示是否启用，编辑后立即作用于新请求和待写事件。部署管理的 bootstrap 通过部署配置管理。

## 规划验收

- A1：逐项回答写入位置、UDF 职责、T+1 链路、真实覆盖范围和线上/本地差异，并给文件或运行证据。
- A2：给出模块归属、标准输入与存储契约、Neo4j 映射、后续 PostgreSQL 模型。
- A3：给出可靠投递、幂等、顺序、事务、共享归属、删除/撤回、元数据补齐，以及已有向量属性的兼容边界。
- A4：给出阶段顺序、测试场景、性能目标测量方法、迁移与回滚条件；性能数字仅为待压测的建议目标。
- A5：明确未核实的在线触发接口、源版本字段和用户待决语义，不将假设写成运行事实。
- A6：明确 flowscope-storage、flowscope-cli、flowscope-core 的 Rust 依赖方向，Python 规则的移植清单，以及仅运行 FlowScope 与 Neo4j 的独立验收场景。
- A7：核实当前 API 的来源字段与鉴权现状；给出服务端写入策略、默认行为、权限不足/来源越界/策略变更的处理，以及写入状态与事务提交时机。
- A8：给出统一 `/api/analyze` 的调度/个人 token 合同与旧调用迁移；个人使用关系、正式血缘和未知表引用的模型边界；策略页面功能、SQLite/API 生效链路及越权/幂等验收。

## 非目标

- 已授权实现首批 Rust 存储、token 策略、策略/审计 UI 和本地隔离演示；不部署生产、不恢复每日入图、不写生产 Neo4j、不变更调度。
- 首期不要求同时实现 PostgreSQL、消息中间件、Flink 运行时采集或整个调度平台改造。
- 不在 neo4j-http-service 新增写入 API 或 Python 存储模块；不把既有向量模型和完整语义检索迁入 Rust 作为首期条件。

## 已确认决策及规划参数

- 2026-11-25 用户确认：临时解析保留独立记录，只有可信来源以稳定身份和版本更新正式图。
- 2026-11-25 用户确认方案 B：FlowScope 自身使用 Rust 提供解析和存储能力，参考现有 Python 项目的规则并移植，取消 Python 写入服务方案。
- 2026-11-25 用户要求将 `/api/analyze` 的 token 与策略页面一起规划，并区分调度正式写入和个人查询标记。设计采用生产严格 Bearer 身份模式；旧匿名调用只在明确迁移窗口降为 parse_only，不写任何 Neo4j 数据。当前接口仍无这些能力，网关层鉴权未核实。
- 用户确认解析成功与图更新成功分别表达；新增个人 usage 写入状态也单独记录。个人“查询”先按提交解析的证据语义落图，实际执行采集不在现有接口能力内。
- “实时”默认建议从可信发布/执行事件被接收计时；首期端到端延迟目标需要按实际 SQL 规模和并发压测后冻结。
- 在线源的正式接口、版本字段、事件订阅能力仍需源系统接入调研；它们不阻止存储层方案形成，但在正式替换之前必须落实，无法取得时仅保存观测。
