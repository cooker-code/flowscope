# 技术设计

## 类型识别

根因在审计映射，解析器已正确返回 select。复用基线 extract_audit_flags 的最终分类与后台校正，增加实际 SQL 回归；不修改前端猜测类型。缺少完整结果的历史 WITH 不误判成 SELECT。

## 保留配置

SQLite 增加单例审计设置表，默认 retention_days=7，与调用方文档分离。管理员 GET/POST /api/audit/settings 使用 retentionDays，复用现有管理员鉴权并返回持久化后的值。审计禁用或缺少管理上下文时明确报错，不扩大匿名管理权限。仅启用审计的模式也执行默认保留。

数据库操作放在 spawn_blocking，以独立连接、短事务读取或保存。迁移可重复执行。输入必须为正整数且可安全转换为时间范围；错误不能覆盖已有值。

## 后台维护

监听启动后，在可停止任务中先清理、再校正类型；设置保存后触发，并周期执行。cutoff=UTC now-retentionDays×24 小时，格式与 ts 一致，严格 ts<cutoff。

每批通过 ts 索引取固定数量 id，初始 200 行，在短事务删除，批间让出；busy 时稍后重试。不得把大批量 DELETE 放在启动前、请求内或审计写入连接锁内。queued 等未完成事件关联行暂保留，状态集合以现有 worker 为准。没有 lineage 表的旧库也应能清理。

只删除 audit_log，不删除 lineage_events：后者承担重试、幂等键和请求状态职责。保护正式图和已有事件行为；不宣称已清理整个事件库。清理条数和错误按批记录，停止信号到达后不启动新批次。

校正仅处理仍保留且可校正的记录，不读取过期且可删除的 result_json。协调两项维护，避免争用和重复遍历历史。

## 查询优化

1. 在同一代表性数据集比较原查询和候选查询的 EXPLAIN QUERY PLAN 与耗时。
2. 优先验证 (sql_type,ts) 复合索引，使类型筛选、时间范围与倒序分页不再全量临时排序。其他索引只按具体查询证据增加。
3. 精确 COUNT 与参数绑定保持；列表不返回 sql_text/result_json。
4. 将 audit→event 每行两次元数据查询改为批量查询或单次连接读取，保持 outcome 优先级和同一读快照。
5. 所有过滤必须在计数和分页前，包括调用方所有权、blocked_policy 合并、unknown 与无 lineage 配置。
6. 单独评估大库首次索引构建成本，不以小库结果推断生产启动时间。

## 页面

PolicyPage 调用方表格下增加全局表单，说明“超过保留时间的审计日志和解析结果将自动删除，已提交血缘不受影响”。保存反馈以服务端成功为准；加载失败不显示假默认成功。复用现有主题、控件和响应式布局，无额外页面或设计改版。

PRODUCT.md 已读取，符合现有产品上下文；没有 DESIGN.md，遵循已有组件。

## 兼容与运行

新表和索引兼容旧库。默认 7 天追溯清理已有审计日志，删除不可由代码回滚恢复；生产应用按部署流程保留备份。在线不执行全库 VACUUM，已释放页由 SQLite 重用。代码实现、本地验证、线上生效分别报告。
