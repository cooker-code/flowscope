# Hive/Spark 前导下划线标识符

## 1. 范围 / 触发条件

当 `AnalyzeRequest.dialect == Dialect::Hive` 的原始 SQL 将 `_name`、
`__semantic_name` 用作 CTE 名、表别名、列引用或列别名时，必须通过
`flowscope_core::analyze()` 的正式解析路径，不得由调用方改名、吞掉 parse error
或仅在批处理脚本中预处理。

该规则适用于 Spark/Hive 合法 regular identifier 的**首字符为 `_`**情形；反引号
标识符仍走 upstream 的 delimited-identifier 路径。

## 2. 签名

实现位于 `crates/flowscope-core/src/dialect_ext/flowscope_hive.rs`：

```rust
impl Dialect for FlowscopeHiveDialect {
    fn is_identifier_start(&self, ch: char) -> bool {
        ch == '_' || self.inner.is_identifier_start(ch)
    }
}
```

`Dialect::Hive::to_sqlparser_dialect()` 已返回 `FlowscopeHiveDialect`，所以 Rust API、
native CLI、HTTP 调用方和由同一 Core 编译的 WASM 使用同一规则。

## 3. 契约

- 前导下划线由 `is_identifier_start` 接受。汉字开头、汉字续字符与别名关键字的规则见 [Hive 别名兼容](./hive-compat-preprocess.md)。其余字符沿用上游 Hive 方言。
- 不修改 `AnalyzeRequest.sql`。报错位置仍对应原始 SQL；不能用将 `_alias` 替换成
  `alias` 的诊断手段作为产品修复。
- 解析成功后，字段血缘保持既有合同：窗口值输入是 `DataFlow`/`Derivation`，
  `PARTITION BY`/`ORDER BY` 输入是带 `metadata.windowRole` 的 `WindowControl`；二者
  不得混合。
- 显式 INSERT 目标列仍由 `metadata.insertTarget` 和目标表
  `metadata.insertTargetMapping` 标注；前导下划线不得改变位置或列名。

## 4. 验证与错误矩阵

| 输入 / 条件 | 预期 |
| --- | --- |
| `SELECT _src.a FROM t AS _src` | Hive 解析成功，Core 可建立血缘 |
| `_cte` CTE、`_src` 表别名、`AS _out` 列别名 | 全部作为标识符解析 |
| `_amount` 是窗口值，`_user_id`/`_paid_at` 是分区/排序字段 | 值边与两条角色分离的 `WindowControl` 边均保留 |
| `INSERT INTO target (_id, _out)` | 目标列名与 one-based position 保留 |
| 数字、Unicode、反引号或关键字 | 与 upstream HiveDialect 一致，不因本修复放宽 |
| 仍含 `ARRAY<STRUCT<...>>` 的 557564 | 前导下划线错误消失，但在复杂类型处继续报错；不能误报本规则失败 |

## 5. 良好 / 基线 / 错误案例

良好：

```sql
WITH _base AS (SELECT _src.amount AS _amount FROM source_table AS _src)
INSERT INTO target_table (_first_amount)
SELECT FIRST_VALUE(_amount) OVER (ORDER BY _amount) AS _first_amount FROM _base;
```

基线：不带 `_` 的同构 SQL 与带 `_` 的 SQL 应得到相同物理 value roots。

错误：把原 SQL 的 `_base` 改成 `base` 后再回放。它只能用于根因诊断，既改变用户
输入也掩盖真实生产路径。

## 6. 所需测试

- 方言单测：`flowscope_hive.rs` 覆盖 `_` CTE、表别名、列别名，且 upstream
  `HiveDialect` 对最小 `_src` 输入仍失败，证明 wrapper 的必要性。
- 集成测试：`crates/flowscope-core/tests/leading_underscore_lineage.rs` 直接调用
  `analyze()`，断言无错误、物理 `sourceTables`/`targetTable`、显式目标映射、窗口
  value/control 分离，以及与无前导下划线同构 SQL 的 physical roots 相等。
- 回归：使用冻结的原 SQL 原文经 native CLI 回放；复杂类型共享样本必须在对应修复
  集成后再次运行。WASM 需要从同一 Core 源码另行构建并验收，不能用 native 成功替代。

## 7. 错误与正确示例

### 错误

```rust
// 只在外部脚本中改名，HTTP/CLI/WASM 的原始输入不会受益。
let rewritten = sql.replace("__semantic_", "semantic_");
```

### 正确

```rust
// 在所有调用方共有的 Hive dialect 中仅接纳 Spark/Hive 合法的 `_` 首字符。
ch == '_' || self.inner.is_identifier_start(ch)
```

### 错误消息为什么可能误导

sqlparser 将未被方言识别为标识符起点的 `_` 作为独立 token，随后可能报
`Expected an expression, found: _`。这说明 lexer/dialect 规则缺口，不等价于作者
SQL 的表达式语义错误；是否还有后续语法缺口必须继续用原文回放确认。
