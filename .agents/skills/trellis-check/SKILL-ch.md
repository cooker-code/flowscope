# 代码质量检查（Code Quality Check）

针对最近写入的代码进行全面质量验证。融合了规范合规、跨层安全性以及提交前检查。

---

## Step 1：识别本次变更内容

```bash
git diff --name-only HEAD
git status
```

## Step 2：阅读任务产物与适用的规范

按顺序阅读当前任务的产物：

- `prd.md`
- `design.md`（若存在）
- `implement.md`（若存在）

```bash
python3 ./.trellis/scripts/get_context.py --mode packages
```

对每一个发生变更的 package/layer，阅读其 spec 索引，并执行其 **Quality Check** 章节的内容：

```bash
cat .trellis/spec/<package>/<layer>/index.md
```

阅读索引中引用的具体规范文件 —— 索引只是指针，不是目标。

## Step 3：执行项目级检查

运行项目的 lint、类型检查与测试命令。修复全部失败项后再继续。

## Step 4：对照清单进行评审

### 代码质量

- [ ] Linter 通过？
- [ ] 类型检查通过（如适用）？
- [ ] 测试通过？
- [ ] 没有遗留的调试日志？
- [ ] 没有被压制的告警或绕过类型安全的写法？

### 测试覆盖

- [ ] 新函数 → 是否添加了单元测试？
- [ ] Bug 修复 → 是否添加了回归测试？
- [ ] 行为变更 → 是否同步更新了现有测试？

### 规范同步（Spec Sync）

- [ ] `.trellis/spec/` 是否需要更新？（新模式、新约定、经验教训）

> 「如果我修复了一个 bug，或者发现了某些非显而易见的事情，是否应该记录下来，以免未来的自己再次踩坑？」→ 如果答案是「是」，请更新相应的 spec 文档。

## Step 5：跨层维度检查（如适用）

如果你的变更仅限于单一层级，可以跳过本步骤。

### A. 数据流（变更涉及 3 个及以上层级）

- [ ] 读路径追踪正确：Storage → Service → API → UI
- [ ] 写路径追踪正确：UI → API → Service → Storage
- [ ] 类型/schema 在各层之间正确传递？
- [ ] 错误是否正确向上传播给调用方？

### B. 代码复用（修改常量、创建工具函数时）

- [ ] 在创建新代码之前，是否搜索过已有相似代码？
  ```bash
  grep -r "pattern" src/
  ```
- [ ] 如果有 2 处及以上定义同一个值 → 是否抽取为共享常量？
- [ ] 批量修改后，是否所有出现处都已同步更新？

### C. 导入与依赖（创建新文件时）

- [ ] 导入路径是否正确（相对 vs 绝对）？
- [ ] 是否存在循环依赖？

### D. 同层一致性

- [ ] 同层中其他使用相同概念的地方是否保持一致？

---

## Step 6：报告与修复

报告发现的违规项，并直接进行修复。修复后重新运行项目级检查。
